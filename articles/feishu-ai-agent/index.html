飞书 + AI Agent 办公全指南：自建应用、豆包与多机器人管理

文 / 龙川武生原稿记录 2026-09-12约 9 分钟
飞书 + AI Agent 办公全指南：自建应用、豆包与多机器人管理
飞书早已不是"另一个微信"。对开发者和效率玩家来说，它是 AI Agent 接入企业工作流的天然底座——消息、文档、表格、会议、审批，几乎一切能力都开放了 API。本文用一条主线串起五种接入姿势：从飞书开发者的底层能力，到豆包代你操作，再到 WorkBuddy 这类第三方 Agent 的双向接入，以及最轻量的 Webhook 推送，最后聊聊多机器人怎么管。
一、飞书基础与开发者能力：从"应用"到命令行 CLI
先说清楚飞书能做什么。它是一套协作操作系统：即时消息（IM）、云文档、多维表格（Base）、日历、会议、审批、妙记，全部打通；更关键的是，这些能力都挂在飞书开放平台之下，对外提供完整的 API。
对企业/团队用户而言，真正的入口是开发者后台（open.feishu.cn）。在这里你可以创建企业自建应用，把任意自动化能力挂进飞书：
飞书：从"应用"到可编程的办公底座
1. 创建企业自建应用：填应用名称、描述、图标即可。
2. 添加"机器人"能力：在「添加应用能力」里找到机器人卡片并添加——这一步让你的应用能在会话里被@、能收发消息。
3. 配置权限（权限管理）：按需给应用开通 im:message、docx:document、base:record 等 scope。权限分 tenant（应用级）和 user（用户级）两类，越敏感越需要管理员审批。
4. 发布版本：应用必须「创建版本 → 发布」后，才能在飞书内被真实使用。
在飞书开放平台点击「创建企业自建应用」（图源：WorkBuddy 官方飞书接入指南）
在「添加应用能力」中为应用添加「机器人」能力（图源：WorkBuddy 官方飞书接入指南）
在「权限管理」中通过「批量导入/导出权限」批量授予 scope（图源：WorkBuddy 官方飞书接入指南）
但光有网页后台还不够"开发者"。真正提高效率的是 飞书 CLI（lark-cli）——飞书官方提供的命令行工具，让你在终端里直接管理应用、调试回调、操作云文档/多维表格/消息，而不必每次都打开网页。它的核心价值有三点：
• 凭证与多应用管理：一条命令即可登记一个应用的 AppID/App Secret，并支持多个应用配置共存（详见第五节）。
• 本地调试飞书能力：在命令行直接读写文档、查表、发消息，适合把飞书当"脚本化的办公后端"。
• 与自动化流水线和 Agent 衔接：很多第三方 Agent（如 WorkBuddy）底层正是通过 lark-cli 的认证模型来对接飞书。
一句话：网页后台负责"定义应用"，CLI 负责"在命令行里驱动应用"。两者配合，飞书就从一个 IM 变成了可编程的工作台。
二、豆包工作伙伴与飞书：以"你本人"的身份行动
先理清一个产品关系：豆包工作是字节旗下"豆包"品牌的 AI 办公产品族，而豆包工作伙伴（原飞书 aily，2026 年 8 月 14 日更名）是其中的核心能力之一——一站式智能体搭建与协作平台，可以加"工作伙伴"、组"工作小队"、设自动化任务、建项目并管资源库。
容易混淆的一点：飞书自身还带着"智能伙伴"能力与妙搭（低代码/无代码应用搭建平台）。从当前实际体验看，它们与豆包工作伙伴尚属相对独立的入口和能力，不要直接划等号。本节聚焦的是豆包工作伙伴这条线。
豆包工作伙伴以"你本人"的身份在飞书内行动，代发行为带"豆包"标记
它和飞书的关系非常深：
• 账号互通：你可以用豆包账号登录飞书，也可以用飞书账号登录豆包企业版。在后者场景下，飞书会把你有权限的数据（姓名、文档、组织信息、消息等）传输给豆包处理。
• 在权限范围内代你操作：工作伙伴能在你已有的权限范围内，连通消息、文档、会议、任务和业务系统，主动帮你推进工作。例如基于文档评论自动收集信息并给方案，或把定时报告、信息汇总直接发给指定成员/群组。
关键点：豆包是以"你本人"的语境在飞书里行动的。它可以代表你发消息、写文档、建任务——但飞书会为这类 AI 代发行为打上身份标记（部分场景呈现为"豆包发送"之类的备注），而且这个标记由系统生成、不可手动删除。这既是合规上的好处（AI 代做的动作可追溯到人、可审计），也是它的边界：你无法让豆包"伪装成纯人工"悄悄发消息。
三、第三方 Agent 接入主流方式：以"应用/机器人"身份（WorkBuddy 为例）
当你要接的不止豆包，而是 WorkBuddy、你自研的 Agent 等第三方智能体时，主流做法是——让 Agent 以"应用的机器人身份"接入飞书。
WorkBuddy 接入飞书：以机器人身份双向协作的链路与两种连接通道
以 WorkBuddy 接入飞书为例（官方操作文档 https://www.workbuddy.cn/docs/workbuddy/Feishu-Guide），完整链路是：
1. 飞书侧建应用 + 加机器人能力 + 配权限（复用第一节步骤）。WorkBuddy 指南要求批量导入一组权限，涵盖消息收发（im:message、im:message:send_as_bot）、文档、多维表格、日历、任务、Wiki 等，确保机器人能真正"干活"而非只能聊天。
2. 拿凭证：在「凭证与基础信息」取得 App ID / App Secret；在「事件与回调」取得 Encrypt Key / Verification Token。
3. Agent 侧配置飞书：在 WorkBuddy 的飞书集成里填入上述凭证。连接模式有两种——WebSocket 长连接（适合无公网 IP 的个人/家庭/办公室用户，开箱即用）和 URL 回调（需公网服务器，填写 Webhook 地址）。
4. 配置事件回调：飞书侧订阅「接收消息」事件 + 「卡片回传交互」回调，让飞书知道把消息发往哪里。
5. 发布应用，然后在飞书搜索机器人名称即可对话。
在「凭证与基础信息」中获取 App ID 与 App Secret（图源：WorkBuddy 官方飞书接入指南）
在 WorkBuddy「助理设置 → 飞书集成」中注册飞书通道（WebSocket 长连接模式）（图源：WorkBuddy 官方飞书接入指南）
在飞书开放平台添加「接收消息」事件，让消息能触发机器人（图源：WorkBuddy 官方飞书接入指南）
创建版本并发布，应用才能正式上线使用（图源：WorkBuddy 官方飞书接入指南）
发布成功后，在飞书里给机器人发任务即可远程驱动电脑上的 WorkBuddy（图源：WorkBuddy 官方飞书接入指南）
这种方式的特点是双向、有身份、能力强：飞书消息能实时触发 Agent，Agent 以 bot 身份回消息，并能在授权范围内调用文档、表格、日历等一整套 API。它和豆包的本质差异在于身份——豆包"像是你本人"，而 WorkBuddy 这类接入是"一个独立的应用机器人"。
四、次要方式：自定义机器人 Webhook 单向推送
如果你的需求很简单——只是让 Agent/脚本把消息推到飞书群，不需要收消息、不需要交互——那么最轻量的方式是自定义机器人 Webhook。
自定义机器人 Webhook：从脚本单向推送消息到飞书群，不可反向
做法：在群聊设置里「添加机器人 → 自定义机器人」，得到一个 https://open.feishu.cn/open-apis/bot/v2/hook/xxxx 的 Webhook 地址；可选地配置"签名校验" Secret，发送时带上 timestamp + sign 防伪造；然后直接 POST 一条消息卡片（JSON）即可上墙。
它的边界非常明确：
• 单向：只能 Agent/脚本 → 飞书，飞书无法反向触发 Agent，也收不到用户回复。
• 无身份上下文：它只是一个群里的"广播喇叭"，不绑定具体用户权限，不能读写你的文档或表格。
• 适用面窄但够用：服务器告警、CI 通知、定时播报、数据日报这类"只发不收"的场景，这是成本最低的方案。
一句话总结第三节与第四节：要双向协作、要调用飞书能力，走"应用机器人"；只要单向播报，走 Webhook。
五、多机器人（多应用）的管理：lark-cli profile 实战
当你的飞书里同时跑着 WorkBuddy、自建通知机器人、测试应用……多个 AppID/App Secret 就开始难管了。我的经验是用 lark-cli 的多 profile 来隔离。
lark-cli 多 profile 管理：按名字隔离凭证，按需切换系统默认 CLI
新增一个机器人（应用）配置：
lark-cli config init \ --app-id <你的AppID> \ --app-secret-stdin \ --name <自定义名字> # 回车后按提示粘贴 App Secret
执行后，这个新配置会写入 lark-cli 的配置文件：
~/.lark-cli/config.json # Windows 下即 C:\Users\<你的用户名>\.lark-cli\config.json
文件里就能看到刚添加的 <自定义名字> 及其凭证。要用哪一个作为系统默认 CLI，切一下即可：
lark-cli profile use <自定义名字>
几条实战建议：
• 命名要有意义：用 workbuddy、ci-notify、dev-test 这类可辨识的名字，别用 app1、app2。
• 按项目/环境隔离：生产、测试、个人各用一个 profile，避免脚本误用错应用的凭证。
• 密钥妥善保管：App Secret 等同于应用密码，不要写进仓库或贴到聊天里；lark-cli 用 --app-secret-stdin 从标准输入读取，比命令行参数更安全。
• 多人协作时统一约定：团队内约定 profile 命名与 config 存放位置，换机器也能快速复现环境。
结语：三种"身份"，怎么选？
把全文收个口——接入飞书的 Agent，本质上是三种身份模型：
身份 代表 方向 能力边界
你本人（AI 代行） 豆包工作伙伴 双向，但在你权限内 带"豆包"标记、不可删，可审计
应用机器人 WorkBuddy 等第三方 Agent 双向 独立 bot 身份，可调用授权 API
自定义 Webhook 脚本/服务播报 单向（仅推送） 无上下文、不能收消息
选型其实很简单：想让 AI 以你的身份办事 → 豆包；想接一个能双向协作的独立 Agent → 自建应用机器人；只想低成本把消息推上墙 → 自定义 Webhook。三者不互斥，实际办公里常常是"豆包管日常、WorkBuddy 管重活、Webhook 管告警"的组合。
飞书把办公变成了可编程的底座，而 Agent 是跑在这套底座上的"数字同事"。先把应用和机器人建起来，剩下的，交给它们去跑。
